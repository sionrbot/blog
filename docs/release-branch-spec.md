# 长期 release 分支与独立内容部署

本文定义发布流程的契约、实现位置和验收要求。操作入口见
[Releasing Sionrbot blog](releasing.md)。使用前检查实时分支规则和生产环境配置；首次设置发布线时按切换步骤操作。

## 决策与范围

- `main` 负责日常开发和内容集成，`release` 是唯一正式发布来源。
- 晋级批准一批源码进入发布线；软件版本 PR 或内容部署操作批准正式发布。
- 软件版本号表示软件版本。纯内容可以独立部署，不增加 patch，不创建软件 Release。
- 每次部署绑定完整源码 SHA；软件版本号不能单独标识线上内容。
- 复用一份发布 workflow、完整验证、双目标构建和部署任务。
- 共用执行队列，以实时 `release` HEAD 判断部署资格，不维护独立候选数据库、内容 tag、人工部署版本号或每目标状态账本。
- 一轮发布结束并完成必要回流后，才晋级下一批无关变化。源码修复按恢复流程处理。

**事实依据：** [发布 workflow](../.github/workflows/release.yml) 已提供固定 merge SHA、完整验证、双目标构建、同次 attempt 产物约束和独立 smoke；[候选脚本](../scripts/release-fixed.ts) 校验版本文件、tag 与公开 Release。

**设计取舍：** HEAD 门禁省去部署历史排序，但 `release` 推进后旧候选不能继续部署，即使新 HEAD 尚未成功。双目标部署不具备原子性；两个结果必须分别报告。

## 晋级与版本管理

1. 确认上一轮结束，发布线的版本记录和修复已回流 `main`。
2. 选择明确的 `main` SHA，从该点建立短期 `promote/*` 分支。
3. 向 `release` 提晋级 PR，记录来源 SHA、完整变化范围和计划使用的发布路径；合并前确认批次符合内容资格，或能产生软件版本 PR。
4. 检查最新 PR head；审核整个批次，而非仅最后一个提交。
5. 使用 merge commit 合并，保留原始功能提交及祖先关系。晋级标题使用不触发版本增长的 `chore:`，不得将整批变化再 squash 为一个功能提交。
6. 软件变化等待面向 `release` 的版本 PR；纯内容批次使用显式内容部署操作。
7. 完成发布、两个目标的部署与 smoke，以及必要回流后，结束本轮。

日常功能 PR 仍 squash 到 `main`，遵循 Conventional Commits。版本 PR 可以继续使用 squash；长期分支之间的晋级、回流使用 merge commit。

只在 `release` 运行一套 Release Please。它生成 `package.json`、`CHANGELOG.md` 和
`.release-please-manifest.json` 的版本变化；`main` 通过回流接收这些记录，不独立计算版本。
版本计算继续遵循现有提交类型规则。非内容白名单变化只表示不能走内容入口，不自动意味着应增加版本；无独立版本的工程变更留在 `main`，随能够产生软件版本 PR 的批次一起晋级，不单独占用发布线，也不伪装成内容部署。晋级审核通过版本预览确认软件批次具有可发布版本。

默认整批晋级，不常态化 cherry-pick。若软件功能已进入 `release`，随后进入的文章不能绕过它单独上线。应在选定晋级节点时安排发布顺序。

## 内容范围

| 路径                                                           | 允许操作         | 约束                                                                     |
| -------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------ |
| `src/content/blog/**/*.md`、`src/content/blog/**/*.mdx`        | 新增、修改、删除 | 包括该目录直属文件；正文和现有 schema 的 frontmatter                     |
| `src/content/pages/about.mdx`                                  | 修改             | 已有页面的作者内容和元数据                                               |
| `src/content/pages/privacy.mdx`、`src/content/pages/terms.mdx` | 修改             | 已有页面的正文和元数据                                                   |
| `src/assets/content/**`                                        | 新增、修改、删除 | 内容专用图片；扩展名限 `.png`、`.jpg`、`.jpeg`、`.webp`、`.avif`、`.gif` |
| `THIRD-PARTY-NOTICES.md`                                       | 修改             | 随内容资源更新署名、许可；不得单独构成内容部署                           |

新内容图片放入 `src/assets/content/`。不为此迁移现有 logo、字体和默认 OG 图片。
现有资源可以被内容引用，但白名单以外的资源修改不属于内容部署。
删除文章和资源仍须通过构建与内部链接检查。

不放行整个 `src/content/pages/` 或 `src/assets/`。新增独立页面通常需要路由或模板；
logo、字体和默认 OG 图片不属于内容专用资源。`src/config.ts`、UI 翻译、组件、样式、
路由、schema、依赖、测试、脚本、workflow 和普通开发文档均不在白名单。

### 路径检查与审核边界

[release-content.ts](../scripts/release-content.ts) 读取软件基线到候选的完整差异：

- 使用 `git diff --no-renames` 与 NUL 分隔输出，检查所有变化路径及操作类型。
- 重命名按删除和新增检查；移出白名单、从软件目录移入内容目录均不得漏检。
- 校验变化两端存在的文件模式，只接受普通文件；拒绝符号链接和子模块。
- 路径规范化检查必须保守，解析失败或历史不完整时拒绝内容资格。
- 非空差异须包含文章、允许的页面或内容图片变化；只有 notices 不能新建内容候选。
- 允许相对软件 tag 的累计差异为空：撤回此前上线的内容可能恰好恢复软件基线。仍须显式批准固定 HEAD，执行全部验证和部署；不另设重复部署去重机制。
- 页面只允许修改，新增或删除这些固定页面不通过内容资格。

路径检查证明范围，不证明 MDX 只有文字。晋级审核必须检查 MDX 的 import、表达式、
嵌入组件和 notices 变化。可沿用已有组件与链接工具；新增脚本、事件处理、计算逻辑或
组件实现走软件路径。路径检查不使用 MDX AST 分类器。内容路径使用与软件路径相同的验证和构建。

## 内容候选资格

令 `S` 为完整候选 SHA，`V` 为 `S` 中一致的 package/manifest 软件版本，
`T` 为公开稳定 Release `vV` 的 tag 解引用到的 commit SHA。

候选必须满足：

1. 来自允许的内容入口，输入为完整 SHA，checkout 精确匹配 `S`。
2. 初次执行时 `S` 等于实时远端 `release` HEAD。
3. `V` 是稳定版本，两个版本文件一致；`vV` 是当前最新公开稳定软件 Release。
4. tag 存在并解析到 commit `T`；`T` 是 `S` 的祖先。没有软件基线时先完成软件发布。
5. `T → S` 的累计差异全部符合内容范围，而非只检查晋级 PR 或最后一个提交。
6. 所有验证与两个生产构建通过；各目标部署前再次检查软件基线和 HEAD 资格。

版本、tag 和基线 SHA 从固定源码及 Release 推导，不作为人工参数。部署前确认 tag 仍指向
准备阶段记录的 `T`。版本相同但累计存在组件、配置或其他非白名单差异时拒绝内容部署。

`T` 是软件资格基线，不是某个目标最后成功部署的源码。公开软件版本曾部署失败时，
合法内容候选可以同时补部署该软件版本，因为完整验证与双目标构建仍执行。
结果记录实际部署 SHA，不声称线上只变化了文章。

## 统一入口与候选记录

[release.yml](../.github/workflows/release.yml) 提供两种入口：

- `pull_request: closed`：仅接受合入 `release` 的同仓库、合法来源版本 PR，使用原事件 merge SHA。
- `workflow_dispatch`：仅用于内容部署，唯一必要人工输入为完整候选 `sha`；正式执行 ref 必须为 `refs/heads/release`。

普通晋级 PR 的合并不自动部署。不得将手动入口变为任意 SHA 的软件发版工具。
workflow 执行 ref 与源码 SHA 分别校验；默认分支保留手动入口定义，并验证 UI/CLI 触发行为。
生产环境限制与凭据访问须配合正式入口配置，不能只依赖候选字符串检查。

两种入口使用以下候选 outputs；运行摘要另外记录 Actions 提供的执行身份：

| 字段                                  | 含义                                          |
| ------------------------------------- | --------------------------------------------- |
| `kind`                                | `software` 或 `content`                       |
| `sha`                                 | 固定源码 SHA                                  |
| `version`                             | 源码软件版本                                  |
| `tag`、`tag-sha`                      | 软件身份；软件候选 tag 创建前预期指向候选 SHA |
| `pr`                                  | 软件版本 PR 编号；内容候选为空                |
| `GITHUB_RUN_ID`、`GITHUB_RUN_ATTEMPT` | Actions 执行及重试身份                        |

候选身份由类型和源码 SHA 确定，重试不改变源码。原事件/dispatch 输入用于恢复候选，
不能将运行时移动的分支作为构建输入。无需向 Git 提交候选 JSON，也无需新增内容 tag。

运行摘要分别列出验证、构建、软件发布、Pages 部署/smoke、Workers 部署/smoke，
以及跳过原因。内容路径的软件发布项标记为不适用。失败、取消、未运行和被取代不能写成成功。
摘要是受 Actions 保留期限约束的运行记录，不承诺永久发布档案。

## 共用流水线与顺序

两种入口共用 `prepare → pages/workers`：

1. 固定并验证候选，执行源代码、翻译、单元、时区、构建、链接和确定性浏览器检查。
2. 分别构建 Pages 与 Workers 的生产输出，保留现有生产路径检查。
3. 使用本次 run 和 attempt 的产物传递方式。
4. 软件路径执行现有幂等 tag/Release 发布与版本 PR 标签更新；内容路径跳过。
5. 两个部署 job 独立检查资格、部署并 smoke。
6. 软件发布后保留版本 PR refresh；内容路径不进行软件发布标签维护。

整个 workflow 共用固定 concurrency group `release-production`，
保留 `queue: max`、`cancel-in-progress: false`。不要按类型、SHA 或触发事件分组。
版本 PR maintenance 使用独立组 `release-pr-release`，避免锁冲突。
队列有限，取消和溢出仍需报告，不能视为发布成功。

各目标实际部署前要求 `candidate.sha == live release HEAD`，并保留相应软件 Release/tag
资格校验。不得只以最新软件版本号判断先后，也不依赖队列按提交顺序启动。
已被后续 HEAD 取代的合法候选跳过部署并记录原因；身份或 tag 冲突应失败，不能归类为普通跳过。

`release` 禁止强推和历史回退，所有正式部署都必须经过该队列。相同 SHA 的重复执行可以
串行重建、部署，不做去重。直接调用托管平台部署不属于此流程。

HEAD 检查不锁住 Git 分支。检查之间分支推进可能造成一个目标成功、另一个跳过；
共享队列防止较新的流水线部署完成后又被旧流水线覆盖，但不提供双目标原子切换。
用新 HEAD 的合法候选完整部署，使两个目标恢复一致。

## 恢复与回流

| 情况                               | 操作                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------- |
| 临时故障且 HEAD 未变               | 重跑原 workflow 全部 jobs，重新验证与构建原 SHA                             |
| 只重跑失败 job，产物来自旧 attempt | 拒绝部署，要求重跑全部 jobs                                                 |
| 未公开软件候选存在源码缺陷         | 检查 tag/Release/draft，按现有流程明确退役候选，修复并创建更高版本的恢复 PR |
| tag/Release 创建中途失败           | 核实远端状态；匹配则幂等继续，冲突或 draft/prerelease 要求明确处理          |
| 软件版本已经公开且源码有缺陷       | 保留原 tag/Release，发布后续修复版本                                        |
| 内容候选有错误                     | 修复后批准新 SHA；不占用或退役软件版本号                                    |
| 一端部署成功，另一端失败           | 分别记录，HEAD 未变时重跑原候选；合法新 HEAD 也可通过完整部署恢复           |
| HEAD 已推进                        | 原候选不得再部署；围绕新 HEAD 恢复，不自动退回旧源码                        |

软件版本 PR 已合并但尚未公开时，不合入无关内容：旧候选会失去 HEAD 资格，新内容候选
也没有对应的公开软件基线。修复推进遵循软件恢复路径。[现有恢复约定](releasing.md#inspect-and-retry)
中的固定 SHA、跳过退役版本和保留公开历史原则继续适用。

发布线修复从 `release` 创建短期修复分支，以 PR 合回。若 `release` 已包含下一批变化，
修复默认随该批次一起验证、发布；此方案不支持绕过它单独部署线上旧版本的补丁。
旧 tag 回滚或多维护版本线需要另外设计，不能通过重跑旧任务实现。

版本 PR 合并后即可创建 `release → main` 回流 PR，不必等待部署成功。
发布线上的软件和内容修复及时回流。用 merge commit 保留祖先关系；冲突在从 `release`
创建的临时分支上合入 `main` 后解决，再向 `main` 提 PR，不将未晋级的开发变化合回 `release`。
纯内容原本来自 `main` 且发布线没有额外修改时，无需制造额外回流提交。

回流包括已进入历史的版本记录，即使对应发布失败；回流成功不能证明上线成功。
下一批晋级前确认所需回流完成。

## 实施清单与切换

| 位置                                                             | 当前职责                                                                                                                  |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `.github/workflows/release-please.yml`                           | maintenance 在 `release` push 后触发，checkout `release`，使用独立并发组                                                  |
| `.github/workflows/release.yml`                                  | 软件和内容双入口、统一候选、共用任务和队列；版本 PR 过滤、refresh；两端使用 HEAD 门禁                                     |
| `scripts/release.ts`、`scripts/release-recovery.ts`              | 正常版本维护、pending 查询和恢复历史面向 `release`；支持固定晋级分支的只读预览                                            |
| `scripts/release-fixed.ts`                                       | 软件候选身份和发布校验、共享候选输出/部署门禁、内容候选校验                                                               |
| `scripts/release-content.ts`                                     | 内容路径、操作、文件模式和累计历史校验；与普通 PR 的 docs-only CI 范围分开                                                |
| `tests/unit/release*.test.ts`                                    | 覆盖双入口、历史计算、恢复、HEAD 门禁及 workflow 契约                                                                     |
| `scripts/check-closeout.ts` 与相关测试                           | 保留日常 PR 的 `main` 默认值；发布 PR 使用 `--base release`，支持内容 dispatch 的候选和双目标结果，不能只按版本 PR 查部署 |
| `docs/releasing.md`、`docs/deploy.md`、`docs/agents/closeout.md` | 操作步骤、目标分支、内容入口及独立结果判定                                                                                |
| `docs/content.md`                                                | 记录内容资源目录和独立部署范围                                                                                            |

以下步骤用于首次建立或迁移发布线；日常发布遵循前文晋级流程：

1. 检查现有 pending 候选、版本 PR、tag/Release 和两端部署。先完成或明确处理旧流程候选，不自动丢弃。
2. 在 `main` 合入并验证流程迁移代码；切换期间不通过旧入口创建新的正式候选。
3. 从审核过且包含迁移代码的 `main` SHA 创建 `release`，保留既有软件 tag 的祖先历史，不强推重写或重新 bootstrap 版本历史。
4. 配置 `release` 保护：禁止直接推送、强推、删除，要求现有 CI/title 检查和 PR 审核；仓库允许 merge commit，日常功能仍按约定 squash。
5. 检查生产环境分支限制、凭据和默认分支上的手动入口。规则与环境配置需要明确的操作授权。
6. 验证仅 `release` 维护版本 PR，正常及恢复路径均使用新目标，停止旧 `main` 发布入口。
7. 迁移本身包含软件文件变化，不能作为内容候选。通过审核的软件版本 PR 建立迁移后的公开软件基线，再使用内容入口。

切换须作为一个协调窗口执行，避免同时维护两套版本 PR。不得将本文视为创建分支、修改保护规则、合并版本 PR 或生产部署的操作授权。

## 验收要求

使用固定提交图和 API fixtures 验证，不以会修改生产状态的测试代替单元契约。

| 场景                                                                   | 预期                                                     |
| ---------------------------------------------------------------------- | -------------------------------------------------------- |
| 两轮整批晋级、版本回流和一次热修复                                     | Release Please 正确计算版本及 changelog，不重复计入历史  |
| 两次内容部署沿用同一软件版本                                           | 均可通过累计 diff 检查，不修改版本文件或创建软件 Release |
| 最后一个提交是文章，累计存在未发布组件修改                             | 拒绝内容资格                                             |
| 固定页面新增/删除、非白名单路径、符号链接、子模块、跨目录重命名        | 拒绝内容资格                                             |
| 仅 notices                                                             | 不创建新内容候选                                         |
| 上线文章后撤回，候选相对软件 tag 差异为空                              | 允许固定 HEAD 内容部署，恢复基线内容                     |
| 仅 docs/CI 等无独立版本的工程批次                                      | 晋级前拒绝，留在 main 等待可发版软件批次                 |
| 合法文章删除、图片增删、页面修改                                       | 路径检查通过，仍执行完整构建与链接验证                   |
| 缺失/非稳定/非最新 Release、版本不一致、tag 改指、基线非祖先、历史不足 | 拒绝候选或部署，指出原因                                 |
| dispatch 从其他 ref 执行、输入不是完整 SHA、checkout 不匹配            | 拒绝内容入口                                             |
| 新内容部署后重跑旧软件候选                                             | 旧候选不覆盖内容，明确记录被取代                         |
| 新 HEAD 尚未成功，重跑旧候选                                           | 仍不允许旧候选部署                                       |
| 同 SHA 重跑全部 jobs / 只重跑失败 jobs                                 | 前者使用新 attempt 产物；后者不能复用旧 attempt 部署     |
| 两目标检查之间 HEAD 推进                                               | 分别记录成功与跳过，不报告全部上线                       |
| 软件 Release 公开但一端失败，随后合法内容部署                          | 通过完整构建部署该软件版本及内容，分别报告两端结果       |
| 软件候选退役与恢复                                                     | 旧候选不能再次发布，新版本跳过退役版本，历史边界正确     |

运行项目要求的 `vp run check`、`vp check`、`vp run lint`、`vp run build`，以及
